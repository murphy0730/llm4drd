# 前端界面与流程重构设计方案（整合版 v2）

> 文档类型：UI/UX 重构规划（文字逻辑）
> 分析基础：在 `docs/frontend_ui_ux_refactor_plan.md`（下称"v1 方案"）基础上，整合对 `frontend/` 全量代码的二次独立梳理（含行号级证据、死代码与样式冗余审计）
> 核心约束：保留全部现有前端功能；本方案不包含代码改动和具体视觉稿
> 编制日期：2026-08-06

## 0. 结论摘要

两轮独立分析得出一致的核心判断：当前系统的问题不是"功能太多"，而是**三类不同抽象层级的信息被平铺在同一层级**——

1. 业务流程阶段（导入、仿真、优化、评审）；
2. 专业分析工具（图谱、甘特、精确求解、插单评估）；
3. 系统级工具（导出、模型连接、健康状态）。

同时，代码级梳理进一步确认了四个实证问题：

- **状态可信性**：实例状态、工作流概览、页面本地状态与历史结果由多套数据源分别维护，实际出现过"仿真标记未运行、却恢复出 4 道工序的历史结果、优化却显示已完成"的矛盾组合（详见 2.1）；
- **状态表达重复**：同一套五步流程进展同时由顶部 flowbar、侧栏 lamp、各页 precheck 条、dashboard Hero 四处独立推导渲染（app_v2.js:1968、3490、4728 等），口径可能漂移；
- **评审页超载**：一个页面承担 4 个 Tab、8 类不同性质的任务，"选中方案"至少有 5 种语义（勾选集/详情/聚焦/AI 推荐/AI 当前方案）；
- **技术层冗余**：样式三层叠代（app_v2.css 含两代规则 + design-system.css 整体覆盖）、12 条旧 hash 映射、无消费方的数据通道与 API 定义并存。

因此本次重构的优先序为：**先解决状态可信度与对象语义，再重组信息架构与界面层级，最后收敛技术冗余**。

整合后的目标架构为六个工作域：**工作台、数据准备、求解中心、决策中心、情景评估、系统工具**。所有导出能力跟随其业务对象出现；所有专业功能完整保留，按"先完成主任务、再按需深入"分层呈现。

#### 规则仿真

- 六种内置规则（ATC/EDD/SPT/CR/FIFO/LPT）+ 已发布策略集

- 22 个可选目标（`GET /optimize/objectives`），勾选 ≤5

- 订单多选（本地）或异步单选（服务端 `review-orders`）、机器类型、工序状态、分组方式

#### 导出、模型连接与系统状态

- 实例 CSV、方案 Excel（优先服务端导出，本地明细兜底且拒绝截断数据，app_v2.js:6940-6983）
- LLM 配置保存/测试（`PUT /config/llm`、`POST /config/llm/test`）
- 健康检查、数据库、任务、版本展示

### 1.3 核心用户流程

**标准排产流程（6 步建议路径）**：

```text
导入（自动强校验）→ 图谱构建（校验通过后自动触发，可不管）→ 规则仿真（建议性基线）
→ 优化求解 → 方案评审（可插单/精确参考/AI 评审）→ 导出交付
```

**最短强制路径（3 步）**：导入 → 优化求解 → 评审勾选 + 导出。

硬性依赖只有两条（app_v2.js:2017-2027、4802）：① 实例存在，否则 6 个业务页被 `navigate()` 拦截退回导入页；② 导出方案要求评审页有候选。图谱、仿真、LLM 配置均为可选环节，仅 precheck 提示不阻断。

**分支流程**：

- 精确求解：可独立于混合优化执行，本质是**另一种求解方式**而非评审之后的动作；
- 插单评估：以仿真或候选方案为基准的完整情景工作流，自带输入、计算与交付闭环；
- 策略复用闭环：优化候选 → 评审发布为策略集 → 用于仿真/优化热启动/精确求解起始解。

## 2. 问题诊断

按"状态可信性 → 信息架构 → 对象语义 → 复杂度呈现 → 技术层"五个主题组织，每项均标注代码依据。

### 2.1 状态可信性：缺少统一、有效的工作流状态（最高优先级）

**问题**：实例信息、工作流概览（`/workflow/overview`）、工作流进度（`/workflow/progress`）、页面本地状态、历史结果五套数据源各自维护，没有统一的**有效性语义**。系统只能表达"做过/没做过"，不能表达"结果是否属于当前实例版本、是否仍有效、是否只是历史记录"。

**实证**（v1 方案实际检查 + 代码确认）：

- 出现过"图谱失效 + 仿真显示未运行却恢复出 4 道工序的历史结果 + 优化显示已完成保留 10 个候选 + 评审显示已选 3/4 + 概览提示下一步是图谱构建"的矛盾组合；
- 前端存在前端兜底推导（`deriveWorkflowSteps`，app_v2.js:1907-1961）与服务端概览两套状态推导，接口不可用时口径可能不一致；
- 换实例时 `resetInstanceDerivedState` 会作废下游状态，但**参数变化**（如重新仿真）不会使优化结果标记过期。

### 2.2 流程引导：有状态提示，无连续推进机制

- 同一套流程进展由四处独立表达：顶部 flowbar（app_v2.js:1968）、侧栏 lamp + review badge、每页 precheck 条（6 种文案分支，app_v2.js:4728-4741）、dashboard Hero 的"下一步：X"；
- `renderPrecheck` 在 `ok` 态直接清空（app_v2.js:3490-3495），用户完成一步后下一步指引随之消失，需自行判断去哪个一级入口；
- 门控反馈不一致：`requires-scene` 禁用态只是透明度降低（app_v2.css:2696），不拦截点击，真正拦截在 `navigate()`（toast + 强制跳回，app_v2.js:2020-2025）——视觉"可点"与行为"被弹走"矛盾。

### 2.3 信息架构：一级导航混合三个抽象层级

九个一级入口中：业务流程阶段（导入/仿真/优化/评审）、分析工具（图谱）、跨阶段汇总（概览）、多对象动作（导出）、系统管理（LLM/系统状态）平铺并列。且主线内部图谱、仿真实为可选环节（无前端硬依赖），却与强制环节同样式同权重呈现。导航承担了"展示系统有什么"，没有承担"帮助用户完成一件事"。

### 2.4 对象语义：评审页超载 + "选中方案"语义不唯一

**评审页同时容纳 8 类不同性质的任务**：候选库、KPI 比较、单方案详情/利用率/甘特、策略发布、插单评估、精确求解、AI 比较、AI 问答。其中精确求解是一种**求解方式**，插单是一条**完整情景工作流**，与"对已有方案做评审"不在同一任务层级。Tab 间靠隐式联动跳转（`send-candidate-to-ai` 直接切 Tab 并回填勾选，app_v2.js:7572-7583）。

**"选中方案"至少有 5 种语义**（代码确认）：

1. 对比/AI 多选集合（≤4，app_v2.js:7526）；
2. 详情/导出的单个聚焦方案（`getSelectedReviewCandidate`，app_v2.js:1570-1574）；
3. 利用率与甘特的聚焦方案（"◎ 详情"联动置顶，app_v2.js:7543-7551）；
4. AI 最近推荐方案（`aiLastRecommendedId`）；
5. AI 自由提问的"当前方案"。

界面用"勾选、详情、当前方案、聚焦、AI 推荐"等不同表达，影响范围不清晰。用户可能以为已选定主方案，实际只是比较勾选；导出页"当前方案"按钮禁用与否依赖评审页中不易察觉的聚焦状态（app_v2.js:4802）。

**"方案"概念体系过载**：系统基准方案库、已存方案集、内置规则（6 种）、启发式参照、基线方案、Pareto 方案、精确冠军、已选方案——至少 8 个相近概念散布各页，chip 文案在"基线/启发式/参照/Pareto/精确"间切换（app_v2.js:3700-3792）。"方案集 + 预排方案"下拉组在 simulate/optimize/插单/exact 四处原样复用（renderPlanSetSelectors，app_v2.js:3274），每次都要重新理解。

### 2.5 复杂度呈现：专业参数与结果默认同时展开

- 混合优化首屏同呈 22 个目标 + 7 项算法参数；
- 精确求解同呈大量目标权重输入；
- 插单工序表同呈 13 列业务与资源字段；
- 评审表同呈候选、多列 KPI 和每行三项操作；
- 利用率长周期一次展开 D1—D51 大量日期列；
- AI 区域先方案摘要又重复完整 KPI 矩阵。

这些内容都有业务价值，问题是没有按"先完成主任务，再按需深入"组织。**宽表横向滚动会让用户失去行对象、字段含义和关键操作的对应关系**——评审表操作区在中等宽度被挤压、插单工序表只能先看到左侧字段，这不是视觉拥挤而是出错概率问题。

### 2.6 实例上下文：当前实例与重新导入的关系不清楚

已有实例时导入页仍首先展示大型上传 Hero，没有区分：首次创建 / 替换当前实例 / 重新校验 / 查看来源与更新时间 / 数据改变后哪些下游失效。场景历史被记录（`llm4drd_v2_scene_history`，app_v2.js:1285-1296）但无可见入口。校验通过后后台自动构建图谱，用户仍停留在导入页，跨页面状态不透明。

### 2.7 重复与不一致的入口

- "导出"分散在 5 处：simulate 页导出、review 行内 ⬇、export 页三种、import 页与 export 页重复的模板下载；
- 实例摘要重复展示于顶栏 KPI 条、dashboard KPI 卡、graph 面包屑、system 上下文卡；
- LLM 状态三处（顶栏 pill、侧栏入口、llm 页），且"已配置"与"已测试可用"不分（顶栏显示已配置，llm 页提示未测试）；
- 图谱失效时顶部提示、状态卡和空状态同时解释同一问题并提供重复入口；
- system 页无任何独有信息或操作，全部为全局状态复读。

重复信息来自不同状态模型，没有提升确定性，反而让用户不知道应相信哪一个。

### 2.8 技术层：样式三层叠代与响应式冲突

- app_v2.css 内含旧 v2 代死规则 + 当前 v3 代主体，design-system.css 再整体覆盖；`:root` 变量两套值不同（`--topbar-h` 78px vs 56px、`--sidebar-w` 260px vs 224px），以后加载者为准；
- 实测 1024×800 视口下，design-system 把侧栏分组切换为横向结构，但布局仍保留侧栏网格宽度，导航文字被截断、主内容偏移——直接影响中等屏幕可用性；
- 死代码与无消费方数据通道（1.5 节清单）增加状态与维护复杂度。此类逻辑需先区分为"补齐入口 / 迁移 / 确认无依赖后停止维护"，不能直接删也不能继续默认加载。

## 3. 重构方案

### 3.1 设计原则

1. **先建立可信状态，再调整界面层级**——所有阶段状态来自同一套有效性判断；
2. **以业务任务组织功能**——一级结构回答"用户要完成什么"，页内回答"用什么工具完成"；
3. **明确操作对象**——实例、基准排产、候选方案、比较集合、主方案、插单情景有清晰边界；
4. **渐进呈现复杂度**——全部专业参数保留，按基础任务/进阶设置/深入分析分层；
5. **结果与来源可追溯**——每个结果能说明来自哪个实例版本、参数、任务和时间；
6. **长任务跨页面持续可见**——离开启动页仍能看到进度、失败原因与完成结果；
7. **导出跟随业务对象**——在用户确认对象的上下文中导出，不依赖其他页面的隐含选择；
8. **渲染层重构、契约不动**——API 层、持久化键、轮询机制、review_runtime 逻辑层保持不变，这是功能零丢失的最大风险隔离带（详见第 5 章）。

### 3.2 新信息架构：六个工作域

```text
工作台（默认首页）
├─ 当前实例与有效性
├─ 正在运行的任务（图谱/仿真/优化/exact/插单）
├─ 当前唯一最重要的阻塞或下一步
├─ 最近可继续使用的结果
└─ 系统健康摘要（吸收原系统状态页有效信息）

数据准备
├─ 数据导入 / 替换（区分无实例与有实例上下文）
├─ 数据校验与问题处理（含校验导出）
├─ 实例信息与数据版本（含实例 CSV 导出、模板下载）
└─ 关系图谱（准备状态层 + 关系分析层）

求解中心
├─ 基准仿真（六规则/策略集、诊断、KPI、甘特、导出）
├─ 混合优化（目标与参数分层、进度、日志、结果恢复）
├─ 精确求解（窗口、预算、权重、局部结果——从评审页解耦）
└─ 可复用调度策略（策略集统一管理视角）

决策中心
├─ 候选方案库（基准/Pareto/启发式参照/精确参考）
├─ 方案比较（比较集合 1-4、KPI 列配置、Δ 与最优标识）
├─ 主方案分析（详情 / 利用率 / 甘特 三个子视图）
├─ AI 决策辅助（继承比较集合与主方案上下文）
└─ 发布与交付（策略发布、主方案导出）

情景评估
└─ 插单评估（分步工作流：基准与策略 → 订单录入 → 工序约束
   → 评估前检查 → 结果与导出）

系统工具
├─ 大模型连接（配置、测试、调用状态细分）
└─ 系统状态与任务诊断（健康、数据库、任务、版本）
```

归类依据（不是简单减少入口，而是按现有依赖自然归类）：

- 图谱依赖实例与校验 → 数据准备；
- 仿真、混合优化、精确求解都生成排产结果 → 求解中心同级（精确求解从评审页解耦，消除"为什么求解在评审里"的认知断点）；
- 方案库、比较、利用率、甘特、AI 都围绕方案选择 → 决策中心；
- 插单有独立输入、计算、交付闭环 → 情景评估；
- 导出分别属于实例、仿真、方案、插单情景、校验 → 跟随各自业务对象；如业务需要集中下载，保留"交付记录/下载汇总"，但不再承担对象选择；
- 原系统状态页无独有操作 → 撤为工作台健康摘要 + 系统工具诊断入口。

### 3.3 统一工作流状态模型（P0 前置）

每个业务资产/阶段至少表达以下状态：

| 状态 | 含义 | 用户可执行动作 |
| --- | --- | --- |
| 未开始 | 当前实例没有该阶段结果 | 开始任务 |
| 运行中 | 当前版本任务正在执行 | 查看进度、继续其他工作 |
| 成功且有效 | 结果属于当前数据版本 | 查看结果、进入下一步 |
| 成功但已过期 | 曾成功，但上游数据或参数已变化 | 查看历史、重新计算 |
| 被阻塞 | 前置条件不满足 | 查看阻塞原因和处理入口 |
| 失败 | 当前任务失败 | 查看错误、修正后重试 |
| 仅历史记录 | 可追溯，但不参与当前决策 | 查看、复制配置、归档 |

状态判断围绕版本链建立：

```text
实例数据版本 → 校验版本 → 图谱版本 → 仿真/求解任务版本 → 方案版本 → 评审与导出版本
```

上游变化**不直接删除下游历史结果**，而是标记"已过期"或"仅历史记录"。工作台、导航状态、页面预检、刷新恢复读取同一结论——前端只保留一个状态推导入口（服务端 `/workflow/overview` 优先，`deriveWorkflowSteps` 作为唯一兜底，两者口径对齐后删除重复表达）。

对 2.1 的矛盾场景，界面应明确表达：图谱已失效；历史仿真（4 道工序）与当前实例（2,000 道工序）不匹配，不能作为当前基准；优化候选属于哪个数据版本，不匹配则标为历史而非"当前已完成"；下一步是重建图谱，历史结果可查看但不混入当前决策。

**状态表达收敛**：步骤状态由主导航（步骤条）统一表达，吸收现有 lamp/flowbar 能力；precheck 条只保留阻断性/错误性提示（校验失败、仿真不可行、优化失败），删除"下一步引导"类文案（6 态分支收敛为 2-3 态）；dashboard Hero 的下一步提示与步骤条同源。

### 3.4 工作台（默认首页）

定位从"统计概览"改为"继续当前工作的入口"，按以下顺序组织：

1. 当前实例、数据更新时间和有效性；
2. 当前唯一最重要的阻塞或下一步；
3. 正在运行的任务（跨页面长任务汇总）；
4. 当前可继续使用的最近结果；
5. 数据规模、方案数量等次级概览（含系统健康摘要）。

顶栏全局区域只保留跨页面持续有用的信息：当前实例、整体有效性、运行中任务、阻塞提醒、LLM 状态。六类规模指标移到工作台与数据准备完整展示，不再占用所有页面的持续空间（解决实例摘要四处重复之一）。

### 3.5 数据准备

**区分两种上下文**：

- *无当前实例*：选择文件 → 结构预检 → 导入 → 强校验 → 图谱准备 → 可求解；
- *已有当前实例*：首先展示实例摘要、来源、更新时间、数据版本、有效性，再提供任务入口：查看校验问题 / 重新校验 / 替换实例 / 下载模板 / 查看或重建图谱 / 导出实例 CSV。

替换数据时，提交前说明哪些下游结果将变为历史。校验通过后继续自动构建图谱，但构建状态必须在当前页面与全局任务区域同时可见，完成后给出清晰继续路径。

**图谱模块分两层**，避免"构建失败提示、空状态和浏览工具"同时争夺注意力：

- *准备状态层*：是否已构建、是否有效、为何失效、是否需重建；
- *关系分析层*：订单搜索、节点/边筛选、布局、选择、详情（现有全部交互保留）。

### 3.6 求解中心

**三种求解方式按目的并列**：

| 求解方式 | 适用目的 | 现有功能保留 |
| --- | --- | --- |
| 基准仿真 | 快速获得基准、验证规则表现 | 六规则、策略集、诊断、KPI、甘特、导出 |
| 混合优化 | 获得多目标候选方案集 | 22 目标、方案数、预算、全部参数、热/冷启动、进度日志 |
| 精确求解 | 有限窗口高质量局部求解 | 起始策略、1-10 天窗口、预算、目标权重、进度、局部甘特 |

**混合优化参数分层**：

- 业务目标层：优化目标、方案数、预算、起始规则/策略；
- 算法控制层（进阶折叠）：种群、代数、粗搜索比例、精炼轮数、ALNS 强度、冷启动；
- 自动建议：按数据规模生成推荐值，允许检查与覆盖；
- 运行前提供配置摘要：优化什么、用多长时间、从什么方案开始。

**策略集统一管理**：策略集是三种求解方式共同依赖的资产，在求解中心提供统一管理视角（名称/来源方案/适用数据范围/稳定 ID）。各求解页仍可就地选择与发布；使用稳定策略 ID 追溯，避免候选排序变化导致名称漂移。

### 3.7 决策中心

#### 3.7.1 两种明确的方案选择语义

只保留两个用户可理解的核心概念，收敛现有 5 种"选中"语义：

| 概念 | 数量 | 影响范围 |
| --- | --- | --- |
| 比较集合 | 1-4 个 | 对比表、AI 比较与推荐 |
| 主方案 | 1 个 | 详情、利用率、甘特、单方案问答、默认导出与发布 |

AI 推荐只是**建议**主方案：接受推荐 → 明确更新主方案；未接受 → 原主方案不变。不再形成第三种长期选择状态。导出按钮文案直接显示主方案名（现状已显示方案名，保留并强化为"主方案"语义）。

来源 chip 术语统一为固定四类：**基准 / 参照 / Pareto / 精确**，全部页面（含 simulate/optimize/插单/exact 的方案选择器）使用同一组件同一文案。

#### 3.7.2 决策流程与界面组织

```text
候选方案库 → 加入比较集合 → KPI 差异与参考方案 → AI 比较/推荐（可选）
→ 确认主方案 → 主方案详情/利用率/甘特 → 发布策略或导出交付
```

界面组织为**左列表 + 右详情的工作台**（对现有"纵向三层长滚动"的重组）：

- 左栏 = 候选方案列表：来源 chip、关键 KPI、勾选、最优标注；启发式参照 chips 收入列表顶部"添加参照"操作区（不必始终占据主要操作区）；
- 右栏 = 随选中切换的详情面板，分 `指标 / 利用率 / 甘特` 三个子视图——把现在对比表 → 利用率卡 → 甘特卡的纵向长滚动改为显式选中行为（替代"◎ 详情"行操作的隐式联动置顶）；
- 勾选 ≥2 时右栏自动切换为**比较视图**：现有 Δ 箭头、行内最优、KPI 列配置（含 localStorage 持久化）、恢复默认全部保留；
- 保存并发布、方案集列表/删除弹窗保留；行内导出保留为快捷方式。

#### 3.7.3 结果分析的渐进呈现

- 比较阶段重点呈现可配置 KPI 与相对差异；
- 确认主方案后再展示详细指标、利用率、甘特；
- 利用率仍支持日/周/月，默认粒度按时间跨度自适应，长周期不一次展开全部日列；
- AI 改为**右侧对话抽屉/面板**，从方案列表"AI 评审"直接唤起并携带上下文（比较集合或主方案），取代"切 Tab + 勾选回填"的隐式跳转；AI 区域保留必要摘要，完整指标从统一方案数据按需查看，不再重复展示完整 KPI 矩阵。

### 3.8 情景评估——插单工作流

功能全保留（全部订单/工序字段、四种录入方式、两种保护策略、合并甘特、导出与全量加载），按任务阶段组织：

```text
1. 选择基准排产与保护策略 → 2. 录入或导入新订单 → 3. 补充工序/前置/资源约束
→ 4. 评估前检查 → 5. 执行评估 → 6. 交期/保护效果/KPI/资源/合并甘特 → 7. 导出或加载全量
```

- 13 列工序字段按业务组组织，不要求同一时刻横向浏览全部字段：标识与所属 / 工艺与时间 / 前置约束 / 机器约束 / 工装与人员约束；
- 录入区与结果区（5 段）分可折叠区块，默认只展开录入区；
- **评估前检查**汇总：缺失字段、无候选资源、前置关系错误、基准方案有效性——减少提交后才发现问题的往返；
- 明确插单结果与原主方案的关系（局部情景，不自动混入方案池）。

### 3.9 系统工具与导出归属

**LLM 状态细分**（解决"已配置≠可用"）：未配置 / 已配置未验证 / 测试成功 / 当前 AI 请求使用大模型 / 使用启发式回退 / 连接失败。全局只显示与当前 AI 能力相关的简明状态；Base URL、模型、密钥留在系统工具。

**导出归属**：

| 导出物 | 归属上下文 |
| --- | --- |
| 实例 CSV、数据模板 | 数据准备—实例信息 |
| 校验结果 Excel | 数据准备—校验问题区 |
| 仿真结果 Excel | 求解中心—基准仿真结果 |
| 主方案 Excel | 决策中心—主方案上下文 |
| 插单结果 Excel | 情景评估—结果区 |

如保留集中"交付"页，它展示已生成的交付物与导出记录（含对象、来源版本、时间），不再让用户猜"当前方案"是什么。

| hash 路由与进度恢复 | 全局框架 | 保留，旧 hash 设兼容映射 |

## 4. 实施建议

### 4.1 总体顺序

```text
P0 状态契约与功能基线（含死代码审计）
  → P1 全局框架与数据准备
  → P1 求解中心（可与数据准备后半段并行）
  → P2 决策中心
  → P2 情景评估
  → P3 交付、系统工具与样式收敛
  → 全量回归与旧入口兼容验证
```

每阶段内部按"**新增结构 → 迁移功能 → 删除旧结构**"小步提交；API 层（`api` 对象）与后端接口全程零改动。

### 4.2 P0：状态契约与功能基线

目标：重构前后对"当前数据和当前结果"的理解一致。

- 建立现有功能—接口—状态—导出物清单（本方案第 1 章即为基线）；
- 为实例、校验、图谱、仿真、优化、exact、评审、插单结果定义版本与有效性；
- 统一工作流概览、进度恢复、导航状态、页面预检的状态来源（单一推导入口）；
- 明确"比较集合"与"主方案"两个选择概念的状态模型；
- 固化大数据性能限制与导出保护条件（分页上限、截断拒绝导出等）；
- 历史结果只读兼容，禁止无提示参与当前流程；
- **死代码审计**（1.5 节清单）：逐项 grep 确认引用关系，区分为"补齐入口 / 迁移 / 停止维护"，确认无依赖的删除——纯删除不碰渲染逻辑，可独立发布。

验收：刷新、切页、重新导入、上游数据变化后，各处状态一致。

### 4.3 P1：全局框架与数据准备

- 落地六工作域导航（任务导向步骤式主导航 + 设置区）；
- 旧 hash 保留兼容映射，避免书签与内部跳转失效；
- 门控表现对齐：无实例时工作流步骤显示真实禁用态（锁标识 + 悬停说明），替代"可点但被弹走"；
- 新旧状态组件**并行运行一个迭代**（步骤条 + 原 lamp 同显），确认推导一致后删旧组件；
- 顶栏收敛为实例/有效性/运行任务/LLM 状态；
- 数据准备区分导入与替换上下文；图谱分两层；
- 确定唯一的布局与响应式样式职责（见 P3 样式收敛的技术准备）。

依赖：P0 统一状态模型。验收：1024/1280/1440 宽度下导航与内容不截断；重新导入的失效影响可解释。

### 4.4 P1：求解中心

- 迁移基准仿真全部功能；
- 混合优化配置分层（业务目标 / 算法控制）+ 运行前配置摘要；
- 迁移完整进度、日志、停滞与结果恢复；
- 精确求解从评审上下文解耦（旧入口保留重定向），标注局部窗口属性；
- 策略集统一管理与稳定标识。

依赖：P0 任务与结果版本。可与 4.3 后半段并行，上线需共同验证。验收：所有目标、参数、启动方式、结果不丢失；长任务跨页面可见。

### 4.5 P2：决策中心（最高风险，建议再拆三个批次）

- 2a **方案库工作台化**：左列表 + 右详情双栏、比较视图切换、术语统一组件；
- 2b **AI 面板化**：抽屉唤起、上下文继承、去除重复 KPI 矩阵；
- 2c **选择语义迁移**：比较集合/主方案两概念落地，"◎ 详情"隐式联动改为显式选中。

迁移约束：`review_runtime.js` 不改（LRU 缓存、AbortController 竞态守卫、订单搜索防抖、96h 初始窗口原样保留），只改渲染层调用点；勾选 ≤4、`PUT /workflow/review` 持久化、列配置 localStorage 键名不变。

验收：任意操作都能回答"对哪几个方案比较、哪个是主方案、导出的是哪个方案"。

### 4.6 P2：情景评估

- 插单分步组织 + 字段业务分组；
- 评估前完整性检查（以现有接口负载为字段契约）；
- Excel/CSV/粘贴/手工四种录入等价测试；
- 明确插单结果与主方案关系。

依赖：P0 基准方案版本 + 4.5 主方案定义。验收：现有请求字段一项不缺。

### 4.7 P3：交付、系统工具与样式收敛

- 导出迁移到对应对象上下文，视需要保留交付记录页；
- LLM 状态细分落地；
- 清理确认无依赖的旧状态路径（先记录运行时读写关系）；
- **样式收敛**：以 design-system 变量为唯一 token 源，app_v2.css 只保留组件结构样式，逐组件核对渲染、分组件提交，不一次性删除旧规则；
- 键盘操作、焦点、错误提示与中等屏幕适配；
- 大实例图谱/甘特/利用率/宽表性能回归。

依赖：业务模块稳定后实施，避免样式与结构重复返工。

### 4.8 验收清单（合并版）

- 六种内置规则与已存策略均可用；22 目标、全部参数、热/冷启动保留；
- 精确求解窗口、预算、权重、局部甘特保留，且标注局部范围；
- 图谱节点/边筛选、搜索、布局、选择、缩放、全屏、详情保留；
- 甘特订单/机器类型/状态/分组/分页/时间窗/停机/非工作时间覆盖保留；
- 比较集合 1-4 个，主方案始终唯一且可识别；KPI 列配置、Δ、最优标识、参照、利用率、AI 保留；
- 插单全部字段、两种保护策略、四种导入方式保留；评估前检查生效；
- 五类导出均可找到且对象明确；
- 刷新与导航切换不会把历史结果误判为当前有效；
- 1024/1280/1440 宽度核心任务不依赖被截断的导航或操作区；
- 大数据量下分页、截断、搜索、性能保护不退化。

## 5. 风险评估

| 风险 | 可能影响的现有功能 | 规避措施 |
| --- | --- | --- |
| 统一状态模型改变旧数据语义 | 刷新恢复、历史仿真、优化候选、评审选择 | 带版本的状态快照；旧结果先按只读历史兼容，不直接删除 |
| review 页交互回归（最高风险） | 勾选上限、持久化、review_runtime 缓存/竞态、甘特初始窗口、订单搜索防抖 | review_runtime.js 不改，只改渲染调用点；以 1.2 节评审功能清单为逐项验收基线；过 `tools/verify_review_ui.py`、`tools/verify_v2_ui.py` 及 tests/ 相关用例 |
| 比较集合/主方案语义迁移错误 | AI、甘特、利用率、发布、导出引用错误方案 | 每类动作建立明确绑定与契约测试；导出前显式显示方案身份 |
| 旧入口失效 | 书签、页面内跳转、自动下一步、测试脚本 | 旧 hash 到新模块的兼容映射，旧 hash 重定向到新页面而非 404；逐步替换内部链接 |
| 门控表现改变导致测试断言失败 | 现有 UI 验证脚本可能断言"点击被弹回导入页" | 测试断言先行修改；同步更新 `tools/verify_v2_full.py` |
| 长任务离开原页面丢失进度 | 图谱、仿真、优化、exact、插单任务 | 任务状态提升到全局层；任务 ID + 实例版本 + 结果版本共同持久化 |
| 信息分层误删专业配置 | 优化目标、算法参数、exact 权重、插单资源约束 | 字段级功能矩阵；只改组织方式，不改请求契约 |
| 图谱重组大实例性能下降 | 全局图谱、订单搜索、节点边过滤 | 保留当前加载上限与聚焦机制；相同数据集做性能基准 |
| 甘特复用调整造成排产表达错误 | 仿真、方案、exact、插单结果 | 保留颜色/分组/过滤/分页/现在线/停机/非工作时间的回归快照 |
| 插单分步录入改变请求组装 | 前置关系、候选机器、工装、人员、保护策略 | 以现有接口负载为字段契约；四种录入方式等价测试 |
| 精确求解被误认为完整全局方案 | 方案库、比较、导出 | 始终标注局部窗口范围；未经明确转换不混入完整方案池 |
| 导出入口迁移后难以发现 | 模板、校验、实例、方案、插单导出 | 对象上下文中提供导出 + 统一交付记录/下载索引 |
| 策略名称随候选排序变化 | 仿真复用、优化热启动、exact 起始策略 | 稳定策略 ID；展示来源方案、版本、发布时间，名称仅作显示 |
| LLM 状态表达不准确 | AI 比较、推荐、问答、回退 | 分离配置/测试/实际调用状态；每次结果注明使用大模型或回退 |
| CSS 合并级联结果变化 | 依赖"app_v2.css 先、design-system 后"的覆盖顺序，选择器特异性漂移 | 以 design-system 变量为基准逐组件核对截图；分组件提交 |
| 清理旧状态路径误伤隐藏依赖 | 评审数据、场景历史、旧 exact 状态 | 先记录运行时读写关系；确认无消费方且测试覆盖后才停止维护 |
| localStorage 键值兼容 | 评审列配置、场景历史、侧栏折叠 | 新结构继续读写原键，不做键名迁移 |
| 流程恢复链路断裂 | `/workflow/progress` 恢复四块状态 | `restoreWorkflowProgress`（app_v2.js:6473-6526）保持不动；每阶段执行"刷新→全状态恢复"手动验收 |

### 风险控制原则

1. 先迁移状态与数据契约，再迁移页面结构；
2. 任何旧结果先降级为历史只读，不做不可恢复删除；
3. 每迁移一个模块，以功能保留追溯矩阵（3.10）验收；
4. 高风险对象——当前实例、主方案、导出目标——在关键操作前始终显式显示；
5. 大数据性能保护、接口负载和导出完整性属于功能，不当作纯技术细节遗漏；
6. 新旧结构并存期间建立兼容层，并设定明确的移除条件；
7. API 层、持久化键、轮询机制、review_runtime 逻辑层全程不动——功能零丢失的可验证性来源于此。

## 6. 最终目标状态

重构后系统不减少任何现有业务能力，但用户应能稳定回答五个问题：

1. 我当前处理的是哪个实例，数据是否有效？
2. 当前流程卡在哪里，下一步应该做什么？
3. 我正在使用哪种求解方式，结果是否属于当前数据？
4. 我在比较哪些方案，哪个方案是当前主方案？
5. 我即将发布或导出的究竟是哪一个对象？

当这五个问题都能在界面中直接获得一致答案时，系统的复杂功能仍然完整存在，但信息架构、操作路径和认知负担将显著降低。
