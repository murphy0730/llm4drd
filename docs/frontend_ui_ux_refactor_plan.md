# 前端界面与流程重构设计方案

> 文档类型：UI/UX 重构规划（文字逻辑）  
> 分析范围：`frontend/` 目录中的页面、组件、交互逻辑和样式，并结合相关后端接口与工作流状态作补充核对  
> 核心约束：保留全部现有前端功能；本方案不包含代码改动和具体视觉稿  
> 编制日期：2026-08-06

## 0. 结论摘要

当前系统的问题并不是“功能太多”，而是以下三类信息同时出现在同一层级：

1. 业务流程阶段，如数据导入、仿真、优化、评审；
2. 专业分析工具，如图谱、甘特图、精确求解、插单评估；
3. 系统级工具，如导出、模型连接、健康状态。

与此同时，实例状态、工作流状态、页面本地状态和历史计算结果由多套数据来源分别维护，使用户可能看到“前置步骤不可用，但后续结果仍显示完成”的矛盾状态。评审页又同时承担方案库、对比、发布、利用率、甘特图、插单、精确求解和 AI 分析，导致操作对象与当前上下文不够清晰。

因此，本次重构应优先解决“状态可信度”和“对象语义”，再调整信息架构与界面组织。建议将系统组织为五个业务工作域：工作台、数据准备、求解中心、决策中心、情景评估；把大模型连接和系统状态收纳为系统工具。所有导出能力跟随其业务对象出现，不再依赖用户记忆其他页面中的隐含选择。

## 1. 现状梳理

### 1.1 前端技术与页面结构

当前前端是单页应用，入口及主要职责如下：

| 文件 | 当前职责 | 现状特征 |
| --- | --- | --- |
| `frontend/index_v2.html` | 页面容器、顶部栏、侧边导航、九个一级视图 | 页面骨架集中，一级入口较多 |
| `frontend/app_v2.js` | 全局状态、接口调用、页面渲染、流程控制、图谱与甘特图交互 | 单文件承载多数业务逻辑，页面状态相互引用较多 |
| `frontend/app_v2.css` | 主体样式、旧版样式补充、后续重构样式 | 多阶段样式叠加 |
| `frontend/design-system.css` | 通用设计变量、布局、卡片和响应式规则 | 与主样式文件存在布局职责重叠 |
| `frontend/review_runtime.js` | 方案评审相关运行时逻辑 | 与主应用共同维护评审状态 |
| `frontend/optimize_progress.js` | 优化进度展示 | 独立维护长任务进度表现 |

当前一级视图共九个：

| 导航分组 | 一级视图 | 主要任务 |
| --- | --- | --- |
| 调度流程 | 数据导入 | 上传生产数据、下载模板、查看当前实例、校验数据 |

| 调度流程 | 优化求解 | 配置多目标与算法参数，执行混合优化 |
| 调度流程 | 方案评审 | 管理候选方案、对比、插单、精确求解和 AI 评审 |

- 异步构建图谱并轮询任务状态；

- 按结构关系、资源关系和其他关系筛选边；
- 图谱自动布局、拖拽、框选、多选、缩放、适配、复位和全屏；

- 执行仿真并展示运行状态；
- 展示不可行诊断及根因详情；
- 展示核心绩效指标；
- 查看仿真结果甘特图；

- 按订单多选和服务端订单搜索；
- 按机器类型、工序状态筛选；

- 当前时间线；

- 22 个可选优化目标，最多选择 5 个；
- 目标方案数量和计算预算；

- 启动异步优化任务；
- 展示真实进度、日志和停滞状态；
- 任务完成后恢复候选结果与排产数据。

- 汇集基准方案、Pareto 候选、启发式参考方案和精确求解参考；
- 默认选择多个方案进入比较，比较集合上限为 4 个；
- 配置对比表 KPI 列；
- 显示相对基准变化、最优单元格和最优方案；
- 查看单个方案详情；
- 对单个方案执行 AI 分析；
- 导出单个方案；
- 发布并管理可复用调度策略集；
- 计算或读取启发式参考方案；
- 按日、周、月查看机器类型利用率；
- 查看单方案甘特图。

#### 1.2.8 方案评审—插单评估

- 从仿真或候选方案中选择基准排产；
- 选择冻结或交期保护策略；
- 新增多个订单及其工序；
- 维护订单、任务、工序、前置关系、加工/周转时间、候选机器、工装和人员等字段；
- 通过 Excel、CSV、粘贴文本或示例数据导入；
- 下载插单模板；
- 执行插单可行性与排产评估；
- 查看承诺交期、插入结果、资源分配、保护效果和 KPI；
- 查看合并后的甘特图；
- 导出插单结果或加载完整排产。

#### 1.2.9 方案评审—精确求解

- 独立启动 OR-Tools CP-SAT 窗口求解；
- 不依赖混合优化即可执行；
- 选择起始规则或策略集；
- 配置 1—10 天求解窗口与时间预算；
- 配置支持或代理计算的目标及权重；
- 展示求解进度；
- 查看局部精确求解结果和甘特图；
- 当前结果属于局部窗口结果，不自动写入完整方案库。

- 使用 1—4 个已选方案作为上下文；
- 展示简要方案摘要和完整 KPI 矩阵；
- 执行方案对比、推荐和自由提问；
- 针对当前方案进行问答；
- 大模型不可用时使用启发式回退结果。

#### 1.2.11 导出、模型连接与系统状态

- 下载数据模板；
- 导出当前实例 CSV；
- 导出当前聚焦方案 Excel；
- 配置 Base URL、模型名称和 API Key；
- 保存并测试大模型连接；
- 查看服务健康、数据库加载、混合优化任务、前端版本和上下文信息。

### 1.3 当前核心用户流程

#### 1.3.1 标准排产流程

```text
导入生产数据
  → 强校验
  → 构建关系图谱
  → 选择规则并仿真
  → 配置多目标优化
  → 获得候选方案
  → 方案比较与评审
  → 选定方案
  → 导出交付
```

#### 1.3.2 精确求解分支

```text
已有有效实例
  → 选择起始规则/策略
  → 配置局部时间窗口、预算、目标权重
  → 执行精确求解
  → 查看局部结果与甘特图
```

精确求解可独立于混合优化执行，因此它实际上是另一种求解方式，而不是必须发生在评审之后的动作。

#### 1.3.3 插单评估分支

```text
选择仿真或候选方案作为基准
  → 选择保护策略
  → 录入/导入新订单
  → 补充工序与资源约束
  → 执行评估
  → 查看交期、保护效果、KPI 和合并甘特图
  → 导出插单结果
```

#### 1.3.4 策略复用闭环

```text
混合优化得到候选方案
  → 评审并发布为策略集
  → 策略集用于规则仿真
  → 策略集用于混合优化热启动
  → 策略集用于精确求解起始解
```

### 1.4 模块依赖关系

| 模块 | 直接依赖 | 产生的下游资产 |
| --- | --- | --- |
| 数据导入 | Excel 文件、实例接口 | 实例及数据规模 |
| 强校验 | 当前实例 | 有效性结论、问题清单 |
| 图谱构建 | 通过校验的实例 | 可浏览关系图谱、后续流程就绪状态 |
| 规则仿真 | 有效实例、规则或策略集 | 基准排产、诊断、KPI、甘特图 |
| 混合优化 | 有效实例、目标、算法参数、可选起始方案 | 候选方案集合、排产和指标 |
| 精确求解 | 有效实例、局部窗口、起始策略 | 局部精确排产 |
| 方案评审 | 仿真结果、优化结果、参考方案 | 比较集合、主方案意图、策略集 |
| AI 决策 | 比较集合或当前方案、大模型配置 | 比较、推荐和问答结论 |
| 插单评估 | 基准排产、新订单及约束 | 插单排产、保护结果、交付文件 |
| 导出 | 当前实例或当前方案上下文 | CSV/Excel 交付物 |

### 1.5 当前实现边界

代码中还存在订单、任务、工序、机器和停机信息更新等前端接口封装，但当前可见页面没有完整编辑入口；后端也存在在线调度、What-if、计划查询、AI 调整排产等尚未接入当前前端的能力。

这些能力不应被误算为“现有可见功能”，本次重构应保留扩展位置，但不应借重构之名扩大业务范围。

## 2. 问题诊断

### 2.1 缺少统一、可信的工作流状态

当前状态由实例信息、工作流概览、工作流进度、本地页面状态和历史结果共同决定，但这些来源没有统一的有效性语义。

实际检查中出现过以下组合：

- 当前实例包含 50 个订单、500 个任务、2,000 道工序和 100 台机器；
- 图谱状态因数据变化被判定为无效；
- 工作流概览将仿真标记为“未运行”，但页面进度中仍恢复出一份只有 4 道工序的历史仿真结果；
- 优化仍显示已完成并保留 10 个候选方案；
- 评审仍显示已完成并选中 3/4 个方案；
- 工作概览提示的下一步却是“图谱构建”。

这说明系统目前只能表达“做过/没做过”，不能稳定表达“结果是否属于当前实例、是否仍有效、是否只是历史记录”。状态矛盾会直接削弱用户对结果的信任，属于最高优先级问题。

### 2.2 有流程状态提示，但缺少连续的任务引导

侧边栏状态灯能提示阶段状态，但主内容区没有形成稳定的流程推进机制。页面在成功状态下构造的下一步信息会被通用预检渲染逻辑清空，因此用户完成一步后，通常仍需要自行判断应该去哪个一级入口。

其结果是：系统具备流程依赖，却主要依靠用户理解和侧边栏跳转完成串联；对首次使用者尤其不友好。

### 2.3 一级导航混合了业务阶段、分析工具和系统设置

当前九个一级入口并不处在同一抽象层级：

- 数据导入、仿真、优化、评审属于业务流程阶段；
- 图谱属于数据关系准备和分析工具；
- 工作概览属于跨阶段汇总；
- 导出属于多个业务对象的动作；
- 大模型连接和系统状态属于系统管理。

用户需要先理解系统内部模块划分，才能找到完成业务任务的位置。导航承担了“展示系统有什么”的职责，却没有充分承担“帮助用户完成一件事”的职责。

### 2.4 方案评审承担过多不同性质的任务

方案评审同时容纳：

- 候选方案库；
- KPI 比较；
- 单方案详情、利用率和甘特图；
- 策略发布；
- 插单评估；
- 精确求解；
- AI 对比与问答。

其中，精确求解是一种求解方式，插单评估是一条完整的情景工作流，它们与“对已有方案做评审”并不处于同一任务层级。将这些能力都放入评审页，使页面入口看似减少，但用户的认知负担被转移到页内标签和状态切换上。

### 2.5 “选中方案”的语义不唯一

当前评审相关状态至少包含：

- 用于对比和 AI 的多选集合；
- 用于详情或默认导出的单个方案；
- 用于利用率和甘特图的聚焦方案；
- AI 最近推荐方案；
- AI 自由提问时的当前方案。

界面上使用“勾选、详情、当前方案、聚焦、AI 推荐”等不同表达，但它们对后续动作的影响范围不清晰。用户可能以为自己已选定主方案，实际只是在比较集合中勾选；也可能在导出时得到另一个隐藏上下文中的方案。

### 2.6 复杂参数和结果信息默认同时展开

典型表现包括：

- 混合优化同时呈现 22 个目标和多项算法参数；
- 精确求解呈现大量目标权重输入；
- 插单工序表同时呈现十余列业务和资源字段；
- 评审表同时显示候选方案、多列 KPI 和每行多项操作；
- 机器利用率在长周期下展开大量日期列；
- AI 区域先展示方案摘要，又重复展示完整 KPI 矩阵。

这些内容本身都有业务价值，问题在于没有按照“先完成主任务，再按需深入”的顺序组织。专业用户也需要频繁扫视和横向移动，才能确认当前上下文。

### 2.7 宽表和长周期数据容易造成上下文丢失

在实际页面检查中：

- 评审表的操作区域在中等宽度下容易被挤压；
- 插单工序表只能先看到左侧部分字段，其余依赖横向滚动；
- AI 的完整 KPI 矩阵在分栏布局中需要局部滚动；
- 利用率视图可一次生成 D1—D51 等大量日期列。

这不是简单的视觉拥挤问题。横向滚动会让用户失去行对象、字段含义和关键操作之间的对应关系，增加填错数据或对错方案的概率。

### 2.8 当前实例与重新导入的关系不清楚

已有实例时，数据导入页仍首先展示大型上传入口，但没有明确区分：

- 首次创建实例；
- 用新文件替换当前实例；
- 对当前实例重新校验；
- 查看导入来源与更新时间；
- 数据改变后哪些下游结果会失效。

代码中虽保存过场景历史信息，但当前页面没有形成可见、可理解的实例历史。校验通过后又会在后台自动构建图谱，而用户仍停留在导入页，进一步加剧跨页面状态的不透明。

### 2.9 状态、提示和操作存在重复或不一致

具体表现包括：

- 图谱失效时，顶部提示、状态卡和空状态可能同时解释同一问题，并提供重复入口；
- 顶部显示“大模型已配置”，模型设置页却可能提示“尚未测试”；
- 模板下载同时出现在导入页和导出页；
- 导出页的“当前方案”依赖评审页中不易察觉的聚焦状态；
- 工作概览、侧边栏状态灯和页面本地状态可能给出不同结论。

重复信息并没有提升确定性，因为它们来自不同状态模型，反而会让用户不知道应相信哪一个。

### 2.10 响应式布局和样式职责存在冲突

主样式文件包含多阶段补充样式，设计系统文件又重复定义顶部栏、侧边栏、页面主体、卡片和断点规则。实际在 1024×800 视口下，设计系统把侧边分组切换为横向结构，但后续布局仍保留侧栏网格宽度，导致导航文字被截断、主内容继续偏移。

因此，当前问题不仅是视觉规范不统一，还会直接影响中等屏幕下的可用性。继续叠加样式会增加回归风险。

### 2.11 存在已维护但未形成用户价值的数据路径

例如场景历史被记录但没有可见入口，部分评审数据会加载但没有清晰的当前消费方，一些旧精确求解状态与当前窗口求解流程并存。它们增加了状态和维护复杂度，却没有帮助用户完成任务。

此类逻辑需要在功能盘点后区分为：继续保留并补齐用户入口、迁移到新模型、或确认无依赖后停止维护。不能直接删除，也不能继续默认加载。

## 3. 重构方案

### 3.1 设计原则

1. **先建立可信状态，再调整界面层级。** 用户看到的所有阶段状态必须来自同一套有效性判断。
2. **以业务任务组织功能。** 一级结构回答“用户要完成什么”，页内再回答“用什么工具完成”。
3. **明确操作对象。** 实例、基准排产、候选方案、比较集合、主方案和插单情景必须有清晰边界。
4. **渐进呈现复杂度。** 保留全部专业参数和字段，但按照基础任务、进阶设置、结果深入分析分层呈现。
5. **结果与来源可追溯。** 每个结果都能说明来自哪个实例版本、参数、任务和时间。
6. **长任务跨页面持续可见。** 用户离开启动页后仍能看到任务进度、失败原因和完成结果。
7. **导出跟随业务对象。** 在用户确认对象的上下文中导出，避免依赖其他页面的隐含选择。

### 3.2 新的信息架构

建议的信息架构如下：

```text
工作台
├─ 当前实例与有效性
├─ 正在运行的任务
├─ 当前业务进度
├─ 待处理问题
└─ 最近结果与继续工作

数据准备
├─ 数据导入 / 替换
├─ 数据校验与问题处理
├─ 实例信息与数据版本
└─ 关系图谱构建与浏览

求解中心
├─ 基准仿真
├─ 混合优化
├─ 精确求解
└─ 可复用调度策略

决策中心
├─ 候选方案库
├─ 方案比较
├─ 主方案详情
├─ KPI / 利用率 / 甘特图
├─ AI 决策辅助
└─ 方案发布与交付

情景评估
└─ 插单评估
   ├─ 基准与保护策略
   ├─ 新订单与工序约束
   ├─ 评估前检查
   └─ 结果、保护效果与导出

系统工具
├─ 大模型连接
└─ 系统状态与任务诊断
```

这一结构不是简单减少入口，而是根据现有依赖自然归类：

- 图谱依赖实例和校验，因此归入“数据准备”；
- 仿真、混合优化、精确求解都会生成排产结果，因此成为“求解中心”的同级方式；
- 方案库、对比、利用率、甘特图和 AI 都围绕方案选择，因此归入“决策中心”；
- 插单有独立输入、计算和交付闭环，因此成为“情景评估”；
- 导出分别属于实例、方案和插单情景，不需要作为唯一入口独立存在；如业务仍需要集中下载，可保留“交付记录/下载汇总”，但不再承担对象选择。

### 3.3 统一工作流状态模型

每个业务资产或阶段不再只使用“完成/未完成”，而应至少表达以下状态：

| 状态 | 含义 | 用户可执行动作 |
| --- | --- | --- |
| 未开始 | 当前实例没有该阶段结果 | 开始任务 |
| 运行中 | 当前版本任务正在执行 | 查看进度、继续其他工作 |
| 成功且有效 | 结果属于当前数据版本，可继续使用 | 查看结果、进入下一步 |
| 成功但已过期 | 曾成功，但上游数据或参数已变化 | 查看历史、重新计算 |
| 被阻塞 | 前置条件不满足 | 查看阻塞原因和处理入口 |
| 失败 | 当前任务失败 | 查看错误、修正后重试 |
| 仅历史记录 | 结果可追溯，但不应参与当前决策 | 查看、复制配置、归档 |

状态判断应围绕以下版本链建立：

```text
实例数据版本
  → 校验版本
  → 图谱版本
  → 仿真/求解任务版本
  → 方案版本
  → 评审与导出版本
```

任何上游变化都不直接删除下游历史结果，而是把它们标记为“已过期”或“仅历史记录”。工作台、导航状态、页面前置检查和刷新后的状态恢复都读取同一结论。

对于前述矛盾场景，界面应明确表达：

- 当前图谱已失效；
- 历史仿真结果只包含 4 道工序，与当前 2,000 道工序实例不匹配，不能作为当前基准；
- 优化候选属于哪个数据版本，若不匹配则标为历史而不是“当前已完成”；
- 下一步是重建图谱，同时允许用户查看历史结果，但不能混入当前决策。

### 3.4 工作台设计逻辑

工作台应成为“继续当前工作”的入口，而不仅是统计概览。

建议按以下顺序组织信息：

1. 当前实例、数据更新时间和有效性；
2. 当前唯一最重要的阻塞或下一步；
3. 正在运行的仿真、优化、精确求解或插单任务；
4. 当前可继续使用的最近结果；
5. 数据规模、方案数量等次级概览。

顶部全局区域只保留跨页面持续有用的信息：当前实例、整体有效性、运行中任务和阻塞提醒。订单、任务、工序、机器等规模指标可在工作台和数据准备中完整展示，避免占用所有页面的持续空间。

### 3.5 数据准备流程

数据准备区先区分两种上下文：

#### 无当前实例

```text
选择文件
  → 文件结构预检查
  → 导入
  → 强校验
  → 图谱准备
  → 实例可用于求解
```

#### 已有当前实例

首先展示当前实例摘要、来源、更新时间、数据版本和有效性，再提供以下任务入口：

- 查看校验问题；
- 重新校验；
- 替换当前实例数据；
- 下载模板；
- 查看或重建图谱。

当用户替换数据时，应在提交前说明哪些下游结果会变为历史。校验通过后可以继续自动构建图谱，但必须在当前页面和全局任务区域显示构建状态，完成后给出清晰的继续路径。

图谱模块内部再区分两层：

- **准备状态层**：是否已构建、是否有效、为何失效、是否需要重建；
- **关系分析层**：订单搜索、节点/边筛选、布局、选择和详情。

这样可以避免“构建失败提示、空状态和浏览工具”同时争夺用户注意力。

### 3.6 求解中心

#### 3.6.1 求解方式并列

把现有三种能力按目的并列：

| 求解方式 | 适用目的 | 现有功能保留 |
| --- | --- | --- |
| 基准仿真 | 快速获得基准方案、验证规则表现 | 六种内置规则、策略集、诊断、KPI、甘特图、导出 |
| 混合优化 | 获得多目标候选方案集合 | 22 个目标、方案数、预算、全部算法参数、热/冷启动、进度与日志 |
| 精确求解 | 对有限时间窗口执行高质量局部求解 | 起始策略、1—10 天窗口、预算、目标权重、进度、局部甘特图 |

用户选择求解方式后，再进入对应配置，不需要先理解精确求解为何位于评审页。

#### 3.6.2 混合优化参数分层

根据当前配置项的业务性质，可自然划分为：

- **业务目标层**：优化目标、目标方案数、计算预算、起始规则/策略；
- **算法控制层**：种群、代数、粗搜索比例、精炼轮数、ALNS 强度、冷启动；
- **自动建议**：基于当前数据规模生成推荐值，但允许用户检查和覆盖。

算法参数全部保留，但不与业务目标争夺首屏注意力。运行前提供配置摘要，使用户能确认“优化什么、用多长时间、从什么方案开始”。

#### 3.6.3 策略集统一管理

策略集是仿真、优化和精确求解共同依赖的可复用资产，应在求解中心提供统一管理视角。各求解页面仍可就地选择和发布策略，但策略名称、来源方案、适用数据范围和稳定 ID 应保持一致，避免候选排序变化导致名称追溯困难。

### 3.7 决策中心

#### 3.7.1 建立两种明确的方案选择语义

建议只保留两个用户可理解的核心概念：

| 概念 | 数量 | 影响范围 |
| --- | --- | --- |
| 比较集合 | 1—4 个 | 对比表、AI 比较与推荐 |
| 主方案 | 1 个 | 详情、利用率、甘特图、单方案问答、默认导出与发布 |

AI 推荐只是建议主方案，不应形成第三种长期选择状态。用户接受推荐后，明确更新主方案；未接受时，原主方案保持不变。

#### 3.7.2 决策流程

```text
候选方案库
  → 加入比较集合
  → 查看 KPI 差异和参考方案
  → AI 比较/推荐（可选）
  → 确认主方案
  → 查看主方案详情、利用率和甘特图
  → 发布策略或导出交付
```

候选方案库保留：基准、Pareto 候选、启发式参考、精确参考、KPI 列配置、相对基准差异、最优标识和逐方案详情。

#### 3.7.3 结果分析的渐进呈现

- 比较阶段重点呈现可配置 KPI 和相对差异；
- 选择主方案后，再展示详细指标、机器利用率和甘特图；
- AI 直接继承比较集合与主方案，不再重复一套完整方案选择器；
- AI 区域保留必要上下文摘要，完整指标从统一方案数据中按需查看；
- 启发式参考方案作为“加入参考”的能力进入候选池，不必始终占据主要操作区域；
- 利用率仍支持日、周、月，但默认粒度根据时间跨度选择，长周期避免一次展开过多日列。

#### 3.7.4 导出与发布

- 实例 CSV：位于数据准备的实例上下文；
- 仿真结果：位于基准仿真结果；
- 主方案 Excel：位于决策中心主方案上下文；
- 插单结果：位于情景评估结果；
- 校验结果：位于数据校验问题区；
- 模板：位于数据导入或插单导入入口。

如果保留“导出与交付”页面，它应展示已经明确生成的交付物和导出记录，而不是再次让用户猜测“当前方案”是什么。

### 3.8 情景评估—插单流程

插单功能字段多、依赖强，适合按任务阶段组织：

```text
1. 选择基准排产与保护策略
   ↓
2. 录入或导入新订单
   ↓
3. 补充工序、前置关系和资源约束
   ↓
4. 评估前检查
   ↓
5. 执行插单评估
   ↓
6. 查看承诺交期、保护效果、KPI、资源与合并甘特图
   ↓
7. 导出结果或加载完整排产
```

全部订单和工序字段、Excel/CSV/粘贴/示例导入、模板下载、两种保护策略、合并甘特图和导出能力均保留。

界面组织上，不应要求用户在同一时刻横向浏览全部工序字段。字段可按以下业务组组织：

- 标识与所属关系；
- 工艺与时间；
- 前置约束；
- 机器约束；
- 工装与人员约束。

评估前检查应汇总缺失字段、无候选资源、前置关系错误和基准方案有效性，减少提交后才发现问题的往返。

### 3.9 大模型与系统状态

大模型状态至少区分：

- 未配置；
- 已配置但未验证；
- 连接测试成功；
- 当前 AI 请求使用大模型；
- 当前 AI 请求使用启发式回退；
- 连接失败。

“已配置”不能等同于“可用”。全局只显示与当前 AI 能力相关的简明状态，Base URL、模型和密钥管理留在系统工具中。

系统状态区继续保留健康检查、数据库、任务和版本信息，并承担跨页面长任务的诊断入口，而不是与业务工作流争夺一级注意力。

### 3.10 功能保留追溯矩阵

| 当前功能 | 重构后归属 | 保留方式 |
| --- | --- | --- |
| Excel 导入、模板、上传进度 | 数据准备 | 保留，按无实例/有实例区分上下文 |
| 强校验、错误警告、校验导出 | 数据准备 | 保留，作为实例就绪前置步骤 |
| 图谱构建和完整交互 | 数据准备 | 保留，分离构建状态与关系浏览 |
| 六种规则和已发布策略仿真 | 求解中心—基准仿真 | 完整保留 |
| 不可行诊断、KPI、仿真甘特图与导出 | 求解中心—基准仿真 | 完整保留 |
| 22 个优化目标与全部算法参数 | 求解中心—混合优化 | 完整保留，基础与进阶分层 |
| 优化进度、日志、停滞处理与结果恢复 | 求解中心—混合优化 | 完整保留，任务状态全局可见 |
| 精确求解窗口、权重、进度和甘特图 | 求解中心—精确求解 | 完整保留，明确局部结果范围 |
| 候选池、参考方案、KPI 列和基准差异 | 决策中心—候选与比较 | 完整保留 |
| 比较、详情、最佳标记 | 决策中心 | 完整保留，统一比较集合/主方案语义 |
| 利用率日/周/月 | 决策中心—主方案分析 | 完整保留，默认粒度自适应 |
| 方案甘特图和所有筛选/覆盖层 | 决策中心及各结果上下文 | 完整保留 |
| AI 比较、推荐、问答、回退 | 决策中心—AI | 完整保留，继承统一方案上下文 |
| 策略发布和管理 | 求解中心/决策中心 | 保留跨模块入口，统一资产管理 |
| 插单全部字段、导入、策略、评估和导出 | 情景评估 | 完整保留，按步骤组织 |
| 实例 CSV、方案 Excel、插单 Excel | 对应业务对象 | 完整保留，消除隐含对象选择 |
| 大模型配置和测试 | 系统工具 | 完整保留，细分状态语义 |
| 健康、数据库、任务、版本 | 系统工具 | 完整保留 |

## 4. 实施建议

### 4.1 总体实施顺序

```text
功能基线与状态契约
  → 统一对象及选择语义
  → 信息架构与全局框架
  → 数据准备和求解中心
  → 决策中心
  → 情景评估
  → 导出、系统工具和样式收敛
  → 全量回归与旧入口兼容验证
```

### 4.2 P0：建立状态与功能基线

目标：先保证重构前后对“当前数据和当前结果”的理解一致。

实施范围：

- 建立现有功能—接口—状态—导出物清单；
- 为实例、校验、图谱、仿真、优化、精确求解、评审和插单结果增加版本与有效性定义；
- 统一工作流概览、进度恢复、导航状态和页面预检的状态来源；
- 明确“比较集合”和“主方案”两个选择概念；
- 固化现有大数据性能限制和导出保护条件；
- 记录历史结果，但禁止其无提示地参与当前流程。

依赖关系：这是后续全部界面重组的前置条件。

验收重点：刷新页面、切换页面、重新导入和上游数据变化后，各处显示的状态一致。

### 4.3 P1：重构全局框架与数据准备

目标：让用户能判断“我现在处理哪个实例、能否求解、下一步是什么”。

实施范围：

- 落地工作台、数据准备、求解中心、决策中心、情景评估和系统工具的信息架构；
- 保留旧 hash/路由映射，避免已有书签和内部跳转立即失效；
- 重组全局状态区，突出实例有效性、运行任务和阻塞项；
- 区分无实例导入和有实例替换；
- 串联上传、校验、图谱构建及完成后的继续路径；
- 分离图谱构建状态与关系浏览状态；
- 确定唯一的布局和响应式样式职责。

依赖关系：依赖 P0 的统一状态模型。

验收重点：1024、1280、1440 等主要桌面宽度下，导航和内容不截断；重新导入前后失效影响可解释。

### 4.4 P1：重构求解中心

目标：把仿真、混合优化和精确求解组织为可理解的同级求解方式。

实施范围：

- 迁移基准仿真及全部规则、诊断、甘特图和导出；
- 将混合优化配置分为业务目标与算法控制；
- 迁移完整进度、日志、停滞和结果恢复能力；
- 将精确求解从评审上下文中解耦，同时明确局部窗口结果属性；
- 统一策略集的选择、发布、来源与稳定标识。

依赖关系：依赖 P0 的任务和结果版本；可与 P1 数据准备后半段并行推进，但上线需共同验证。

验收重点：所有目标、参数、启动方式和结果不丢失；长任务跨页面持续可见。

### 4.5 P2：重构决策中心

目标：使候选、比较、主方案、AI 和交付围绕同一套方案对象工作。

实施范围：

- 建立候选池、比较集合和主方案流程；
- 保留可配置 KPI、基准差异、最佳标识和参考方案；
- 将详情、利用率、甘特图和单方案 AI 统一绑定主方案；
- 将比较 AI 统一绑定比较集合；
- 简化重复 KPI 展示的数据路径；
- 方案发布和导出前明确显示对象、来源版本和有效性；
- 收敛重复的评审数据加载和缓存状态。

依赖关系：依赖 P0 的方案语义和 P1 求解中心输出。

验收重点：任意操作都能回答“对哪几个方案比较、哪个是主方案、导出的是哪个方案”。

### 4.6 P2：重构情景评估

目标：把插单从评审标签转为独立、可校验的情景工作流。

实施范围：

- 迁移基准方案与保护策略；
- 分阶段组织订单和工序录入；
- 保留 Excel、CSV、粘贴和示例导入；
- 增加提交前完整性汇总；
- 保留承诺交期、资源、保护效果、KPI、甘特图和完整导出；
- 明确插单结果与原主方案的关系。

依赖关系：依赖 P0 的基准方案版本和 P2 决策中心的主方案定义。

验收重点：现有请求字段一项不缺，导入与手工录入得到一致的校验结果。

### 4.7 P3：交付、系统工具与技术收敛

目标：消除重复入口和样式冲突，完成全局一致性。

实施范围：

- 将导出能力迁移到对应对象，并视业务需要保留交付记录；
- 细分大模型配置、连接测试和实际调用状态；
- 保留系统健康与任务诊断；
- 清理确认无用户价值且无依赖的旧状态路径；
- 逐步收敛重复样式和断点规则；
- 完成键盘操作、焦点、错误提示和中等屏幕适配；
- 对大实例图谱、甘特图、利用率和宽表执行回归测试。

依赖关系：依赖前述业务模块稳定后实施，以免样式与结构重复返工。

### 4.8 建议的重构验收清单

- 六种内置仿真规则和已保存策略均可用；
- 22 个优化目标、全部算法参数、热启动和冷启动均保留；
- 精确求解窗口、时间预算、目标权重和局部甘特图均保留；
- 图谱节点/边筛选、搜索、布局、选择、缩放、全屏和详情均保留；
- 甘特图订单、机器类型、状态、分组、分页、时间窗口、停机和非工作时间覆盖均保留；
- 比较集合支持 1—4 个方案，主方案始终唯一且可识别；
- KPI 列配置、基准差异、最佳标识、参考方案、利用率和 AI 均保留；
- 插单全部订单/工序/资源字段、两种保护策略和全部导入方式均保留；
- 校验、实例、仿真、方案和插单导出均能找到且对象明确；
- 页面刷新和导航切换不会把历史结果误判为当前有效结果；
- 1024、1280、1440 宽度下核心任务无需依赖被截断的导航或操作区；
- 大数据量下原有分页、截断、搜索和性能保护不退化。

## 5. 风险评估

| 风险 | 可能影响的现有功能 | 规避措施 |
| --- | --- | --- |
| 统一工作流状态时改变旧数据语义 | 刷新恢复、历史仿真、优化候选、评审选择 | 使用带版本的状态快照；旧结果先按只读历史兼容，不直接删除 |
| 调整模块归属导致旧入口失效 | 书签、页面内跳转、自动下一步、测试脚本 | 保留旧 hash 到新模块的兼容映射，并逐步替换内部链接 |
| 比较集合与主方案语义迁移错误 | AI、甘特图、利用率、发布和导出可能引用错误方案 | 为每类动作建立明确绑定和自动化契约测试；导出前显示方案身份 |
| 长任务离开原页面后丢失进度 | 图谱、仿真、混合优化、精确求解、插单任务 | 任务状态提升到全局层；任务 ID、实例版本和结果版本共同持久化 |
| 信息分层时误删专业配置 | 优化目标、算法参数、精确权重、插单资源约束 | 建立字段级功能矩阵；重构只改变组织方式，不改变请求契约 |
| 图谱重组造成大实例性能下降 | 全局图谱、订单搜索、节点与边过滤 | 保留当前加载上限、搜索和聚焦机制；使用相同数据集做性能基准 |
| 甘特图复用调整造成排产表达错误 | 仿真、候选方案、精确结果、插单结果 | 保留颜色、分组、过滤、分页、当前线、停机和非工作时间的回归快照 |
| 插单分步录入改变请求组装 | 前置关系、候选机器、工装、人员、保护策略 | 以现有接口负载作为字段契约；对 Excel/CSV/粘贴/手工输入做等价测试 |
| 精确求解被误认为完整全局方案 | 方案库、比较和导出 | 始终标注局部窗口范围；未经明确转换，不自动混入完整方案池 |
| 导出入口迁移造成能力难以发现 | 模板、校验 Excel、实例 CSV、方案/插单 Excel | 在对象上下文中提供导出，同时提供统一交付记录或下载索引 |
| 策略名称随候选排序变化 | 仿真复用、优化热启动、精确起始策略 | 使用稳定策略 ID；展示来源方案、版本和发布时间，名称只作显示 |
| 大模型状态表达不准确 | AI 比较、推荐、问答和回退结果 | 分离配置、测试和实际调用状态；每次结果注明使用大模型或回退逻辑 |
| 样式收敛造成跨页面视觉回归 | 侧栏、顶部栏、表格、卡片、响应式布局 | 分阶段迁移；建立关键页面多宽度截图基线，不一次性删除旧规则 |
| 清理旧状态路径误伤隐藏依赖 | 评审数据、场景历史、旧精确求解状态 | 先记录运行时读写关系；只有确认无消费方且测试覆盖后才停止维护 |

### 5.1 风险控制原则

1. 先迁移状态与数据契约，再迁移页面结构；
2. 任何旧结果先降级为历史只读，不做不可恢复删除；
3. 每迁移一个模块，都以功能保留追溯矩阵做验收；
4. 高风险对象——当前实例、主方案、导出目标——在关键操作前始终显式显示；
5. 大数据性能保护、接口负载和导出完整性属于功能，不应被当作纯技术细节遗漏；
6. 新旧结构并存期间建立兼容层，并设定明确的移除条件。

## 6. 最终目标状态

重构后的系统不减少任何现有业务能力，但用户应能稳定回答五个问题：

1. 我当前处理的是哪个实例，数据是否有效？
2. 当前流程卡在哪里，下一步应该做什么？
3. 我正在使用哪种求解方式，结果是否属于当前数据？
4. 我在比较哪些方案，哪个方案是当前主方案？
5. 我即将发布或导出的究竟是哪一个对象？

当这五个问题都能在界面中直接获得一致答案时，系统的复杂功能仍然完整存在，但信息架构、操作路径和认知负担将显著降低。
