# 甘特图订单全选状态修复设计

## 背景与根因

甘特图的通用多选组件当前把“全部选中”压缩提交为空数组，调用方也把空数组解释为“全部”。但本地甘特图为避免大实例首次渲染全部数据，又会在空数组且数据超过安全阈值时自动选择第一个订单。两种语义共用同一个空数组，导致用户主动全选并点击组件外部提交后，选择状态回退为第一个订单。

## 目标行为

- 大实例首次进入甘特图时，仍默认只选择第一个订单，保留现有性能保护。
- 用户主动点击“全选”时，组件保留并提交所有订单 ID。
- 点击组件外部关闭下拉面板后，甘特图展示全部订单，不回退为单个订单。
- 全选状态下继续使用机器分组，避免订单层级在全部数据下过重。
- 机器类型等复用该多选组件的筛选保持等价行为：全量 ID 与无筛选的结果一致。

## 方案

修改通用多选组件的提交逻辑：始终提交当前工作集中的实际 ID，不再把“全部选中”压缩为空数组。

订单筛选收到完整订单 ID 集合后，现有甘特逻辑会把它识别为多选，使用 `__all__` 作为下游展示模式并保留全部排程条目。初始状态仍然是空数组，因此大实例首次进入时的首单兜底不变。这样无需引入新的哨兵值，也无需扩大调用方接口。

“全部取消”仍沿用现有空数组语义；本次只修复主动全选的状态丢失，不改变取消全选的产品语义。

## 数据流

1. 打开订单多选面板时，工作集由当前选择初始化。
2. 点击“全选”后，工作集加入全部订单 ID，并同步选项勾选态和摘要。
3. 点击组件外部时关闭面板，提交完整工作集。
4. `app.ganttOrderMulti[canvasId]` 保存全部订单 ID。
5. 页面重绘时识别为多选/全部订单，过滤结果包含全部订单，甘特图进入机器分组模式。

## 测试与验收

- 增加前端回归测试，证明全选提交的是完整 ID 集合而非空数组。
- 覆盖点击组件外部触发关闭和提交的路径，确保提交后不会回退首单。
- 验证大实例初始空状态仍保留首单兜底。
- 运行相关前端契约测试及完整关联测试，确认订单与机器类型多选没有回归。

## 非目标

- 不调整甘特图的数据量阈值或分页策略。
- 不修改服务端取数模式下的单订单选择器。
- 不重构通用筛选组件或引入新的全局状态模型。
